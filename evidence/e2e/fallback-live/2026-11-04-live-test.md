## The one defect found

The qwen fallback target `auto/qwen3.8-flash` **does not exist on the magpie
gateway**. The gateway's `/v1/models` answer enumerates the real ids; qwen is
served only as `opencode-go/qwen3.8-flash` (there is no `auto/qwen3.8-flash`).
The plugin correctly detected the corp 429 and rewrote the request, but the
rewritten route returned:

```
404: {"message":"magpie knows no model \"group/auto-qwen3-8-flash\"; did you
mean opencode-go/qwen3.8-flash, auto/gemini-3.8-flash, bishengai/gemini-3.8-flash? ...",
"type":"not_found_error"}
```

`PI_AI_ERROR` (404 not_found) is not an eligible failover code, so the plugin
stopped instead of hopping to `auto/claude-haiku-5-5`, and the turn ended in
error.

Root cause is upstream of the plugin: the live profile itself declares the
phantom model `auto/qwen3.8-flash` under `llm-pi-ai.providers.magpie.models`
(`~/.dsh/profiles/web/cordis.patch.yml`). The previous offline suite only
checked that routes parse and the row composes; it never sent a real request to
magpie, so an invalid model id could not be caught.
